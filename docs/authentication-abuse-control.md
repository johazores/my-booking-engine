# Authentication abuse control

The sign-in and sign-up browser POST handlers validate canonical email identities and password length before reserving attempts. Identity emails reject control characters, Unicode default-ignorable formatting (including joiners, variation selectors, and tag characters), directional marks, bidi controls, and unpaired Unicode surrogates; optional registration names receive the same checks. Credential form bodies are limited to 8 KiB before parsing, below the general mutation limit. Sign-up also validates the optional display name before admission, rejecting unsafe invisible characters in the raw value before trimming (including boundary BOM characters). Malformed UTF-16 passwords are rejected before hashing or verification. The same shared validators run again inside the authentication services so alternate callers cannot bypass the policy. Invalid credential input does not consume the per-identity or deployment-wide quota; syntactically valid rotating identities can still exhaust it, so trusted-source edge protection remains necessary. Reservations use PostgreSQL conflict updates and the database clock, not process-local memory, so all replicas share limits.

Each route has a separate 15-minute fixed-window budget:

| Route | Per canonical email | Deployment-wide |
| --- | ---: | ---: |
| Sign-in | 10 | 5,000 |
| Sign-up | 4 | 1,500 |

Each admitted request, including successful authentication, spends its per-identity quota first and then the deployment-wide quota. Requests rejected by an exhausted identity budget do not consume the shared deployment quota. This prevents repeated attacks against one already-limited email from exhausting the global allowance for unrelated users. A request denied by the global quota still consumes its identity allowance; the two checks are intentionally fail-closed and are not a single transactional reservation. Account keys are HMAC-SHA256 digests derived using the separate 32-byte deployment secret `SF_AUTH_ABUSE_SECRET`; only digests, operation, scope, window, and count are persisted. The secret must be canonical unpadded base64url and identical across replicas. Missing/invalid secrets fail closed with a generic error. Rotating the secret resets per-identity windows and must be coordinated across replicas. Old windows are opportunistically pruned after 48 hours.

The database applies `date_bin` with `statement_timestamp()` and a conditional atomic `ON CONFLICT` increment. A single statement returns both the admission decision and the database-clock seconds remaining in the rejected fixed window, avoiding a clock-read race at window rollover. Concurrent requests cannot exceed either count limit, including when distinct identities race for the last shared slots. The shared quota covers identity-admitted requests, not all HTTP requests; edge-level request flooding still needs separate trusted-source/WAF controls. Denied browser requests redirect to the same form with database-derived `Retry-After` between 1 and 900 seconds. Because browsers follow the HTTP 303 and do not expose the intermediate redirect header to the rendered form, the redirect also carries a bounded `retry` seconds parameter. The sign-in/sign-up pages display an approximate rounded-up wait, validating the query value against the 15-minute budget. This query parameter is display-only and never controls quota enforcement, which remains exclusively in PostgreSQL. Missing, malformed, or out-of-range query values show generic wait feedback. Redirects are HTTP 303, not 429, and must not be counted as edge-level HTTP throttling.

## In-process scrypt capacity protection

Authentication scrypt work (registration hashing, sign-in password verification, and unknown-email timing padding) is now bounded to **two concurrent derivations per application process**, with **16 FIFO waiting requests** and a **10-second maximum queue wait**. Each configured scrypt derivation requires roughly 64 MiB of working memory, so this prevents a burst of admitted requests from launching unbounded memory-intensive crypto jobs. A full queue or expired wait fails closed and returns the existing generic authentication server-error feedback; no credential/session write proceeds. Slots are released even if scrypt fails. Unexpected scrypt runtime failures propagate to the generic server-error boundary rather than being reported as incorrect credentials. These are fixed conservative per-process safeguards, not distributed request quotas or proof of deployment-wide capacity. Load-test the actual production process/memory limits before tuning.

The sign-in and sign-up routes pass their request abort signals through quota admission, authentication services, password derivation, and the final session-persistence boundary. An already-aborted request spends no identity or global quota. If the request aborts while an identity quota write is in flight, that write may still complete, but the independent global quota write is skipped. If the global write has already started, both counters may be consumed. Neither write is refunded or forcibly cancelled.

When the application runtime aborts a request signal, its queued work is removed from the crypto FIFO promptly; an already-running scrypt operation cannot be cancelled, so its slot remains occupied until completion and its result is discarded. Registration and sign-in recheck abort state after asynchronous database reads and before starting user/session writes. Sign-in also rechecks the active user state under a PostgreSQL row lock at session insertion, denying a stale credential read after suspension. A disconnect cannot roll back a database write that has already begun. This is best-effort abandoned-work protection, not an atomic cancellation guarantee.

The new domain regressions cover pre-aborted requests, cancellation between the identity and global quota writes, and cancellation after the global write starts. `scripts/auth-abuse-abort-wiring-contract.test.mjs` guards both browser route signal handoffs and the repository/domain boundary. The guarded PostgreSQL integration suite additionally checks that a pre-aborted request creates no identity quota row; this database test still requires an explicitly disposable target.

The PostgreSQL identity/global admission budgets still apply first, and trusted-source edge/WAF protections are still required. The new dependency-free concurrency, overflow, failure, and timeout tests do not replace Node 24/load testing.

## Still open

- No trusted client-source identity is available in the app runtime. Do not trust caller-supplied `X-Forwarded-For`. Verify edge header ownership and add trusted per-source protection independently.
- Global caps can temporarily deny legitimate users during sustained abuse. Monitor privacy-safe operation/outcome counts and tune with real production evidence. This does not replace DDoS/WAF protection.
- Sign-up now maps duplicate-address failures to the same generic browser error as other registration failures. However, successful registration still creates an immediate session, so the success/failure distinction can reveal account existence. Full remediation requires a real email verification/recovery lifecycle, not a fake success response.
- The checked-in migration and integration suite require live Node 24 and disposable PostgreSQL validation before production rollout. The Phase 2 checklist remains open until that evidence and the missing protections exist.

Run `npm run test` and guarded `npm run test:database` with the documented disposable target.
