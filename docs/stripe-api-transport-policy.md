# Stripe API transport policy

## Purpose

SF sends Stripe secret API keys and commercial payment idempotency keys only from server-side provider adapters. Those values are credential and money-movement authority, so outbound Stripe REST calls use one narrow transport boundary instead of relying on ambient Fetch defaults or caller-provided request metadata.

The boundary is `src/server/payments/stripe-api-transport.ts`. It is used by the Stripe integration health probe, PaymentIntent authorization/capture/release/refund adapter, hosted Checkout adapter, PaymentIntent reconciliation, and refund reconciliation.

## Reviewed API surface

The transport accepts only HTTPS requests to `api.stripe.com` with no alternate port, userinfo, query string, or fragment. The implemented operations are intentionally explicit:

- `GET /v1/balance` for the integration health probe;
- `POST /v1/payment_intents` and `POST /v1/payment_intents/{pi}/capture|cancel`;
- `GET /v1/payment_intents/{pi}` for reconciliation;
- `POST /v1/refunds` and `GET /v1/refunds/{re}`;
- `POST /v1/checkout/sessions` and `GET /v1/checkout/sessions/{cs}`.

The outbound target must also be an exact canonical string URL of at most 2,048 characters. SF rejects URL objects and text that WHATWG URL parsing would silently normalize, including dot segments, percent-encoded dot segments, uppercase hostnames, explicit default ports, and surrounding whitespace or control characters. Empty `?` and `#` delimiters are rejected explicitly because parsed `search` and `hash` are empty for those inputs. All currently implemented Stripe adapters already use fixed canonical string URLs. This is a credential-bearing transport restriction, not a new Stripe provider capability.

Adding another Stripe endpoint is a provider-capability change and must update this allowlist deliberately rather than gaining access through a generic URL or Request object.

## Credential and request metadata boundary

GET requests may carry only the Stripe Authorization header. POST requests may carry only Authorization, `Content-Type: application/x-www-form-urlencoded`, and `Idempotency-Key`; a POST without a bounded printable idempotency key or serialized form body fails before network I/O. Provider constructors also apply the same 4,096-character secret-key ceiling as tenant integration configuration.

The serialized POST body is capped at 256 KiB of UTF-8 data. Current SF Stripe operations are much smaller; this is an application-owned resource ceiling so an internal regression cannot turn the credentialed transport into an unbounded request-body channel.

The final Fetch call is projected from reviewed fields instead of spreading arbitrary `RequestInit`. SF forces `cache: no-store`, `credentials: omit`, manual redirects, an empty/no-referrer policy, `keepalive: false`, and empty integrity metadata. Caller-owned method, headers, body, and signal are materialized once before validation and Fetch; throwing getters fail as non-retryable invalid requests rather than changing authority after validation. A native AbortSignal brand check rejects forged signals before network I/O, and an already-aborted native signal produces abort-shaped timeout evidence. During response streaming, native signal state and native event-listener methods remain authoritative even if a signal instance shadows its `aborted` or listener properties. Listener registration is followed by an abort recheck, and synchronous stream-read failures clean up the listener before propagating. A completed stream is checked once more before replay, so a late timeout cannot become an accepted response. The same original active signal is preserved so the existing local timeout authority remains intact. Framework/runtime extensions such as Next.js fetch metadata or Node/Undici dispatcher fields are not forwarded.

Manual redirects are important at this credential-bearing boundary: SF must observe an unexpected 3xx response and let the provider adapter fail closed rather than automatically following it with the Stripe bearer key, POST body, or idempotency key. Stripe documents secret API keys as authentication credentials that must be protected, and mutating API calls use `Idempotency-Key` for safe operation identity.

## Response resource and deadline boundary

The shared transport does not return to an adapter when only response headers have arrived. It acquires the complete response body first while the caller-owned abort signal remains authoritative. This means the provider adapters' existing timeout remains active through response-body delivery even when an injected test/custom Fetch implementation does not wire its returned stream to that signal. The same native-signal deadline also covers **initial Fetch promise settlement**, not just response streaming: if a custom or stalled Fetch ignores abort, SF rejects promptly with abort-shaped timeout evidence. A Fetch response arriving after that timeout is discarded and its stream is cancelled best-effort; late Fetch rejections are consumed without changing the already reported timeout. Native AbortSignal methods and state are used rather than instance-shadowable properties.

Stripe REST response bodies are capped at 4 MiB and at 16,384 streamed chunks, including empty chunks. This second limit prevents endless zero-byte streams or millions of tiny chunks from exhausting CPU or per-chunk allocation overhead while remaining below the byte ceiling. The transport grows a single bounded byte buffer rather than retaining an allocation per chunk; valid responses are replayed with their exact acquired bytes. A malformed or oversized `Content-Length` fails before buffering, and the transport independently counts actual stream bytes so chunked or differently framed responses cannot bypass the ceiling. Provider chunks must be `Uint8Array` values and are copied before retention using native typed-array byte-length and copy operations, not shadowable chunk instance properties; malformed chunks fail as retryable unknown provider evidence. A failed stream read or size violation best-effort cancels the upstream reader, and the reader lock is released after both successful and failed acquisition; a malformed reader release is also normalized as retryable unknown provider evidence. Locked response bodies, throwing response metadata, failed stream reads, and malformed replay metadata are retryable unknown provider evidence, not raw upstream exceptions. Cancellation errors cannot mask that classification or caller-owned abort authority. A real timeout that has already expired when Fetch returns takes precedence even over malformed declared response metadata. The completed body is replayed as an unread response for the existing adapter-specific JSON/status validation path. A null-body response also goes through the same replay/metadata validation instead of returning the original response: this preserves native timeout authority during body inspection, rejects throwing status metadata as retryable `UNKNOWN`, strips stale wire representation headers, and retains legal no-body HTTP statuses (such as 204) without inventing a body.

Because Fetch runtimes may expose decoded body bytes while retaining wire-representation headers, replay removes `Content-Encoding` and `Content-Length`. Status, status text, media type, Stripe headers, and other response metadata remain available to adapters.

A response-boundary failure occurs after provider I/O may already have happened. SF therefore materializes it as retryable `UNKNOWN` payment-provider evidence rather than a deterministic invalid request. Existing durable payment/refund idempotency and reconciliation paths remain responsible for safe recovery. A caller-owned timeout remains a timeout because the transport throws an abort-shaped error when that signal fires during body acquisition.

## Failure and settlement behavior

This transport boundary does not reinterpret payment success, create new provider-success authority, or weaken tenant/payment locking. Existing provider adapters still own HTTP/error normalization, exact money/reference validation, timeout classification, and durable payment/refund settlement. An unexpected redirect or response remains non-success provider evidence; it is never payment truth.

The boundary also does not add client-side Stripe calls. Raw card data remains outside SF server payment APIs; hosted customer payment remains Stripe Checkout, and provider truth still comes from persisted provider references plus signed callbacks or explicit reconciliation.

## Stable provider stream-result snapshots

The Stripe REST response reader now snapshots each completed stream-read result into a plain record before passing it to bounded response buffering, whether or not the caller supplied an abort signal. Nonconforming provider/custom Fetch readers cannot change validated `done` or `value` properties on a later access; completed results do not inspect `value`. Malformed read results remain retryable `UNKNOWN` provider evidence with best-effort cancellation, and caller-owned native abort authority remains intact. This is a same-pattern sweep of the JSON/form/webhook stream-result boundary, not a change to provider endpoint, credential, or settlement authority. Focused tests are checked in; full Node 24 and live-provider validation remain open.

## Coherent response metadata and cleanup

Stripe API responses now snapshot the upstream body, headers, status, and status text once before inspecting the declared length or reading bytes. The same copied headers authorize length checks and are replayed to payment adapters after wire-representation headers are stripped. A custom Fetch cannot pass validation with one header set and expose a different set after a stream read; one-shot or throwing response accessors are normalized to retryable `UNKNOWN` provider evidence without leaking their errors.

If metadata or declared-length validation fails after body acquisition, SF cancels that captured stream best-effort rather than accessing a possibly stateful `response.body` getter again. Bodyless responses declaring positive bytes fail closed, except HTTP 304, which can legitimately describe the length of a selected representation without transmitting it. An HTTP 304 remains a non-success provider status; this exception does not prove payment or settlement. Caller-owned native abort still outranks malformed metadata, including when a bodyless response claims missing bytes after its metadata getter aborts the caller. This is the Stripe-side similar-concern sweep of Travelport response metadata snapshot handling.

The focused TypeScript tests cover one-read streamed/bodyless metadata, header mutation during reads, cleanup for throwing accessors and malformed lengths, missing bodies, the HTTP 304 exception, and abort precedence. These tests are checked in but require the repository Node 24 toolchain to execute; isolated Node 22 behavioral checks do not replace the full test suite.

## Unencoded response-length integrity

For streamed responses with declared `Content-Length` and no non-identity content coding, the transport requires the buffered payload byte count to match the declaration. Truncated and excess identity responses fail as retryable `UNKNOWN` provider evidence before adapter parsing. This runs within the existing reader-cancellation and native-abort boundary. Encoded responses are exempt from equality because Fetch can expose decompressed bytes while retaining the compressed wire length; both types remain bounded by actual bytes and chunk count. Replay continues stripping wire representation headers. Regression tests cover mismatch directions, encoded compatibility, and abort precedence. Full Node 24 validation remains outstanding.

## Content-Encoding classification and identity-length integrity

The shared dependency-free HTTP content-coding classifier distinguishes absent or explicit `identity` encoding from an actual content coding. An upstream `Content-Encoding: identity` (including case variants) no longer bypasses the existing exact `Content-Length` check. Empty, malformed, overlong, or excessively enumerated content-coding lists fail before reading the response body, with best-effort stream cancellation and the existing retryable `UNKNOWN` classification. Valid compressed or otherwise encoded representations still skip wire-length equality because Fetch may expose decoded bytes, but retain the actual-byte and chunk ceilings. The transport continues to strip wire representation headers on replay. This policy applies to both Stripe and Travelport provider boundaries via a pure HTTP parsing helper; it does not assert provider settlement truth. Focused TypeScript tests are checked in; full Node 24 and live-provider validation remain open.

## Partial-response and framing authority

SF never sends HTTP Range requests to Stripe. A 206 Partial Content response, a 2xx response carrying Content-Range, or a response with both Content-Length and Transfer-Encoding now fails at the shared REST transport before any PaymentIntent, Checkout, refund, or integration-health adapter can interpret it as complete provider truth. Malformed framing is retryable UNKNOWN evidence after possible provider I/O, not a deterministic decline or permission to retry a commercial write with a new key. Error statuses such as 416 may retain Content-Range for downstream non-success classification. The shared content-coding parser also accepts only HTTP SP/HTAB around coding tokens, rejecting vertical tabs, form feeds, and Unicode whitespace that JavaScript trim previously accepted. Rejected response streams are cancelled best-effort and local timeout authority remains unchanged. Focused tests are checked in; full Node 24, database, and live Stripe validation remain separate gates.

## Encoded zero-length response integrity

A provider response with `Content-Length: 0` cannot contain a nonempty decoded Fetch body, even when `Content-Encoding` names a compressed representation. The shared response-length predicate now rejects this impossible evidence as retryable `UNKNOWN` after provider I/O. Positive encoded wire lengths remain exempt from decoded-byte equality because Fetch can transparently decompress; identity representations still require exact equality. Caller-owned abort precedence, upstream cancellation, and the existing response ceilings remain unchanged. Regression tests cover multiple codings and timeout precedence. Full Node 24 and live Stripe validation remain open.

## Stripe conflict and external-dependency failure authority

Stripe distinguishes a concurrent same-key request from a mismatched idempotency replay. A bare HTTP 409, or the explicit `idempotency_key_in_use` error code on HTTP 400/409, is **retryable unknown payment truth**, not a definitive duplicate or failed charge: Stripe may still be processing the first request. Only HTTP 400/409 with the exact `idempotency_error` / `idempotency_key_reused` type/code pair is a non-retryable `DUPLICATE` failure. Recovery must retain the original durable operation identity and idempotency key; it must not issue a new commercial write with a new key merely because of a conflict. Stripe's API reference also states that a concurrent conflict does not cache an idempotent result.

HTTP 424 means a Stripe dependency failed and is classified as retryable `PROVIDER_UNAVAILABLE` before any untrusted error-body card or idempotency hint. A 402 without actual card-decline evidence remains retryable `UNKNOWN`, not a customer decline or definitive invalid request. PaymentIntent, refund, and Checkout creation use the same payment-error classifier. Read-only PaymentIntent/refund/Checkout reconciliation also treats 409/402 as retryable unknown provider truth and 424 as retryable provider unavailability, while retaining the explicit 404 missing-reference behavior.

These classifications matter because the existing tenant-owned payment, Checkout, refund, and commercial-amendment services fail durable claims only for non-retryable provider errors. Ambiguous conflicts and external failures must remain recoverable through their existing idempotent/reconciliation paths. No automatic retry with a fresh key, new provider capability, or browser-proven settlement is introduced. Focused adapter and classification regression tests are checked in; Node 24/full repository and live Stripe validation remain separate gates.

The Checkout provider now distinguishes GET session reconciliation from POST session creation at its internal request boundary. GET uses the shared read-only Stripe lookup classifier (including exact 404 missing-reference semantics), not the payment-write idempotency classifier. The same Stripe HTTP 424 provider-unavailable policy also applies to the read-only integration health probe, which reports only normalized health/failure codes and never raw dependency diagnostics. Regression coverage spans PaymentIntent authorization/capture/release/refund, Checkout creation/retrieval, PaymentIntent/refund lookups, and the integration probe.

## Exact idempotency mismatch evidence

Stripe writes classify `DUPLICATE` only when HTTP 400/409 provides `type: idempotency_error` together with `code: idempotency_key_reused`. An incomplete, unknown, in-flight, or wrong-status idempotency hint remains retryable `UNKNOWN` under existing durable-key reconciliation. Untyped issuer-decline hints and a `card_error` carrying an idempotency code also cannot prove a definitive card decline. The shared classifier applies across direct PaymentIntent writes, refunds, and hosted Checkout without changing tenant scope or retry keys. Full Node 24 and live Stripe verification remain outstanding.

## Canonical pre-provider payment write context (October 27, 2026)

The shared `stripe-payment-write-input.ts` guard now runs before Stripe network I/O for PaymentIntent authorization, capture, authorization release, refunds, and hosted Checkout creation. Direct adapter callers cannot silently case-fold or trim tenant/booking UUIDs, idempotency keys, or payment currencies into different commercial operations. Only canonical lowercase UUIDs, unchanged valid idempotency keys, exact supported uppercase currencies, and positive bigint minor-unit amounts no greater than JavaScript's safe-integer limit may reach Stripe. Malformed inputs fail as non-retryable `INVALID_REQUEST`, with no provider request. The payment amount bound prevents a Stripe response that uses JSON numbers from becoming impossible to reconcile exactly.

Checkout also validates its optional caller-supplied clock before computing the Stripe expiry. Invalid dates and overflowing expiries fail before any provider request. These are adapter defense-in-depth checks, not a replacement for server-side tenant membership, booking ownership, pricing, payment authorization, persisted idempotency, or reconciliation. Existing provider-returned money and ownership checks remain mandatory after Stripe I/O.

Regression tests exercise the same invalid context matrix across all four PaymentIntent/refund writes and Checkout creation, asserting zero outbound requests. Full Node 24 repository tests, Prisma/PostgreSQL, production build, and live Stripe validation remain separate unverified environment gates.
